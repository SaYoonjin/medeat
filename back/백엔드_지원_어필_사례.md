# 백엔드 직무 지원 어필 사례 정리

- 기준 프로젝트: MEDEAT 백엔드
- 목적: 자기소개서, 포트폴리오, 면접 답변에서 사용할 수 있는 백엔드 경험 사례 정리
- 작성 원칙
  - 구조는 `상황 -> 해결방법과 그렇게 생각한 이유 -> 성과` 순서로 통일했습니다.
  - 정량 성과는 `MEDEAT_리팩토링_원본.md`에 남아 있는 baseline/재측정 값을 우선 사용했습니다.
  - 별도 실측값이 없는 항목은 코드 구조에서 확인 가능한 수치, 예: Top-N 개수, 테이블/인덱스/제약 수, 실행 주기, 정책값을 중심으로 정리했습니다.
  - 현재 코드에는 리팩토링 기록과 일부 구현 상태가 완전히 일치하지 않는 부분도 있으므로, 면접에서는 "리팩토링 기록 기준으로 측정했다" 또는 "현재 구현/개선안 기준"을 구분해 설명하는 것이 안전합니다.

## 1. 식단 추천 API 중복 조회 제거

### 상황

- 식단 추천 기능은 사용자의 하루 섭취량, 목표 칼로리, 탄단지 비율, 고칼로리 음식 대체 후보를 한 번에 계산해야 했습니다.
- 추천 과정에서 `고단백 저지방`, `건강 대체식`, `저탄수`, `저지방` 후보군을 여러 단계에서 다시 조회하고 있었습니다.
- 고칼로리 음식별 대체 후보도 음식마다 별도로 조회해, 한 요청 안에서 이미 계산한 후보군을 재사용하지 못하는 구조였습니다.
- API baseline은 `GET /api/diet/recommend` 평균 `2523.08 ms`, P95 `2575.25 ms`로 사용자 체감 지연이 큰 편이었습니다.

### 해결방법과 그렇게 생각한 이유

- 먼저 추천 결과를 만드는 흐름을 후보군 단위로 분해했습니다.
- 같은 요청 안에서 재사용 가능한 후보군은 한 번만 조회하고, 이후 단계에서는 메모리에서 필터링하도록 정리했습니다.
- 대체 음식 추천도 음식마다 후보를 다시 읽는 대신, 대체 후보 풀을 먼저 만든 뒤 조건에 맞게 매칭하는 방식으로 바꿨습니다.
- 이 방식을 선택한 이유는 SQL 튜닝보다 먼저 애플리케이션 레벨의 중복 계산을 제거해야 병목 위치를 정확히 볼 수 있다고 판단했기 때문입니다.
- 또한 추천 로직은 조건이 많아질수록 쿼리 수가 쉽게 늘어나는 영역이라, 후보군 재사용 구조를 먼저 잡아두면 이후 기능 확장에도 유리하다고 봤습니다.

### 성과

- 추천 API 평균 응답시간: `2523.08 ms -> 2247.61 ms`
- 추천 API P95: `2575.25 ms -> 2356.41 ms`
- 평균 응답시간 `10.91% 감소`, P95 `8.50% 감소`
- 단일 최적화만으로 큰 폭의 개선은 아니었지만, 이후 SQL 병목 최적화로 이어질 수 있는 기반을 만들었습니다.

## 2. 추천 음식 SQL의 `ORDER BY RAND()` 병목 개선

### 상황

- 추천 음식 추출 SQL이 `ORDER BY RAND() LIMIT 9` 방식이었습니다.
- `food` 테이블 데이터가 `220,004건`인 상태에서 매 요청마다 전체 후보를 랜덤 정렬하므로, 데이터가 많아질수록 DB 정렬 비용이 커지는 구조였습니다.
- SQL baseline에서 추천 음식 SQL representative actual은 `912 ms`, CLI wall-clock 평균은 `639.82 ms`였습니다.

### 해결방법과 그렇게 생각한 이유

- 전체 row를 랜덤 정렬하는 방식 대신, `max food_id`를 기준으로 랜덤 pivot id를 생성하는 방식으로 바꿨습니다.
- pivot 뒤쪽 후보를 먼저 조회하고, 개수가 부족하면 pivot 앞쪽 구간에서 부족한 만큼 보충하도록 설계했습니다.
- 이 방식은 완전한 랜덤 정렬보다 통계적 랜덤성은 약할 수 있지만, 추천 서비스에서는 "매번 다양한 후보를 제공"하는 것이 핵심이고 전체 정렬까지 필요한 요구사항은 아니라고 판단했습니다.
- PK 범위 기반 접근은 인덱스를 활용할 수 있어 데이터 증가 시에도 비용이 완만하게 증가할 가능성이 높다고 봤습니다.

### 성과

- 추천 음식 SQL wall-clock 평균: `639.82 ms -> 296.58 ms`
- 추천 음식 SQL wall-clock P95: `718.45 ms -> 322.80 ms`
- representative actual: `912 ms -> 0.115 ms`
- wall-clock 평균 `53.65% 감소`, P95 `55.07% 감소`, representative actual `99.99% 감소`
- 22만 건 규모의 food 데이터에서 DB 정렬 병목을 직접 줄인 SQL 최적화 사례로 설명할 수 있습니다.

## 3. 약 검색/상세 조회 Cache-First 전환

### 상황

- 약 검색과 상세 조회는 공공 API에 의존하고 있었습니다.
- 로컬 DB에 이미 약 정보가 저장되어 있어도 외부 API를 먼저 호출하거나, fallback 과정에서 중복 호출이 발생할 여지가 있었습니다.
- 외부 API는 응답 지연, 장애, 호출 제한에 영향을 받기 때문에 의료 정보 조회처럼 사용자 신뢰가 중요한 기능에서는 안정성 리스크가 컸습니다.
- baseline은 약 검색 평균 `1110.98 ms`, 약 상세 평균 `1529.22 ms`였습니다.

### 해결방법과 그렇게 생각한 이유

- 검색은 로컬 약 이름 캐시를 먼저 조회하고, 결과가 없을 때만 외부 API를 호출하도록 변경했습니다.
- 상세 조회는 로컬 row에 이름, 효능, 복용법, 주의사항 등 핵심 설명 텍스트가 있으면 외부 API 호출 없이 즉시 반환하도록 early return을 추가했습니다.
- 검색과 상세 보조 메서드를 공통 흐름으로 묶어 같은 캐시 전략을 쓰도록 정리했습니다.
- 이렇게 판단한 이유는 외부 API가 "원천 데이터 보강" 역할이어야지, 매번 사용자 요청의 필수 경로가 되면 응답시간과 장애 전파 범위가 커지기 때문입니다.
- 로컬 캐시를 우선하면 성능과 장애 격리를 동시에 얻을 수 있다고 봤습니다.

### 성과

- 약 검색 평균 응답시간: `1110.98 ms -> 76.94 ms`
- 약 검색 P95: `2670.77 ms -> 146.08 ms`
- 약 검색 외부 API 호출 수: `1.00/request -> 0.00/request`
- 약 상세 평균 응답시간: `1529.22 ms -> 37.07 ms`
- 약 상세 P95: `2660.93 ms -> 66.02 ms`
- 약 상세 외부 API 호출 수: `1.00/request -> 0.00/request`
- 약 검색 평균 `93.07% 감소`, 약 상세 평균 `97.58% 감소`, 외부 API 호출 `100% 감소`

## 4. 약품 정보 Hybrid 수집과 fallback 보강

### 상황

- 약품 데이터는 한 API만으로는 완성도가 부족했습니다.
- 낱알식별 API는 외형, 각인, 색상, 이미지 정보가 강했지만 효능/복용법/주의사항 텍스트가 부족할 수 있었습니다.
- EasyDrug API는 효능/복용법 등 텍스트 정보가 있지만 외형 정보가 충분하지 않을 수 있었습니다.
- 일부 약품은 API 응답 자체가 비어 있어 상세 페이지 스크래핑까지 고려해야 했습니다.

### 해결방법과 그렇게 생각한 이유

- 약 이름 검색 시 낱알식별 API와 EasyDrug API를 모두 호출하고, `itemSeq`를 기준으로 병합했습니다.
- `itemSeq`가 같은 데이터는 비어 있는 필드를 서로 채우는 merge 전략을 사용했습니다.
- 이름 검색이 실패하면 괄호 제거, 함량 제거, 제형명 제거 등 정규화된 검색어로 재시도했습니다.
- 그래도 정보가 부족하면 nedrug 상세 페이지를 Jsoup으로 가져오고, `효능효과`, `용법용량`, `사용상의주의사항` 헤딩 기반으로 본문을 추출했습니다.
- 특히 주의사항 큰 덩어리 안에서 `이상반응`, `상호작용`, `보관` 섹션을 정규식으로 분리했습니다.
- 이 구조를 선택한 이유는 데이터 출처마다 강점이 달라, 단일 API 의존보다 "식별자는 하나로 맞추고 필드는 출처별로 보강"하는 방식이 더 안정적이라고 봤기 때문입니다.

### 성과

- 약품 상세 데이터 병합 기준을 `itemSeq`로 통일했습니다.
- 약품 정보 보강 경로를 `낱알식별 API -> EasyDrug API -> 이름 정규화 재검색 -> nedrug 스크래핑`의 다단계 fallback으로 구성했습니다.
- 효능, 복용법, 주의사항, 상호작용, 이상반응, 보관법 등 사용자에게 필요한 상세 필드를 더 안정적으로 채울 수 있게 했습니다.
- 외부 API 응답이 불완전한 경우에도 상세 조회 결과를 생성할 수 있는 회복 경로를 확보했습니다.

## 5. 복약 알림 스케줄러 N+1 쿼리 제거

### 상황

- 복약 알림 스케줄러는 1분마다 실행되어 하루 `1,440회` 동작합니다.
- 기존 구조는 스케줄러가 전체 medication을 조회한 뒤 Java에서 현재 시각과 맞는 알림 대상을 골랐습니다.
- 알림 대상이 정해진 뒤에는 약마다 오늘 복용 로그를 다시 조회했고, 사용자 push 설정도 중복 조회될 수 있었습니다.
- 대표 시각 `08:00`, 알림 대상 `12건` 기준 DB query가 `13회`, DB wall-clock이 `4080.97 ms`였습니다.

### 해결방법과 그렇게 생각한 이유

- 현재 시각에 알림이 필요한 대상만 SQL에서 조회하도록 변경했습니다.
- 오늘 복용 로그는 medication id 집합 기준으로 한 번에 집계 조회하도록 정리했습니다.
- 같은 실행 안에서는 사용자별 push 설정 조회 결과를 재사용하도록 설계했습니다.
- 스케줄러는 반복 실행되는 작업이므로, 단일 요청보다 "작은 낭비가 하루 종일 누적되는 비용"이 크다고 판단했습니다.
- 따라서 전체 조회 후 애플리케이션 필터링보다 DB에서 조건에 맞는 대상만 가져오는 방식이 더 적합하다고 봤습니다.

### 성과

- 대표 시각 `08:00`, 알림 대상 `12건` 기준 DB query 수: `13회 -> 3회`
- DB wall-clock: `4080.97 ms -> 963.71 ms`
- query 수 `76.92% 감소`, DB wall-clock `76.39% 감소`
- 하루 `1,440회` 반복되는 배치의 누적 DB 부하를 줄였습니다.

## 6. 복약 알림 시간 문자열 정규화

### 상황

- 복약 알림 시간은 `medication.intake_time`에 쉼표 문자열로 저장되어 있었습니다.
- 알림 대상 조회는 `REPLACE + FIND_IN_SET` 함수 조건으로 문자열을 검사했습니다.
- 이 방식은 일반 인덱스를 활용하기 어렵고, 잘못된 시간 토큰이나 중복 시간이 들어가도 DB 차원에서 정리하기 어려웠습니다.
- 기존 API와 DTO는 여전히 문자열 기반 `intakeTime`을 사용하고 있어 한 번에 완전히 바꾸면 영향 범위가 컸습니다.

### 해결방법과 그렇게 생각한 이유

- 기존 문자열 컬럼은 유지하되, 알림 조회용 `medication_schedule` 보조 테이블을 추가하는 방식을 선택했습니다.
- `intake_time` 단일 인덱스와 `medication_id + intake_time` 유니크 인덱스를 추가했습니다.
- 복약 등록/수정 시 문자열 컬럼과 스케줄 테이블을 함께 동기화했습니다.
- 스케줄러 조회는 `medication_schedule.intake_time = ?` 동등 비교로 변경했습니다.
- 이 방식을 선택한 이유는 기존 API 계약을 유지하면서도, 가장 병목이 되는 스케줄러 읽기 경로만 먼저 정규화할 수 있기 때문입니다.

### 성과

- 알림 시간 정규화 테이블: `0개 -> 1개`
- 보조 인덱스: `0개 -> 2개`
- 대상 조회 조건: `REPLACE + FIND_IN_SET` 함수 조건 `1개 -> intake_time 동등 비교 1개`
- 대표 입력 `08:00, 12:00, 08:00, invalid` 기준 동기화 row: `2개`
- 검증: `MedicationServiceRefactoringUnitTest.addMedicationShouldNormalizeAndDeduplicateScheduleRows` 통과 기록

## 7. 복약 로그 중복 저장 방지

### 상황

- 복약 로그는 복약 순응도 통계와 PDF 리포트의 원천 데이터입니다.
- 사용자가 복용 버튼을 중복 클릭하거나 네트워크 재전송이 발생하면 같은 복약 이벤트가 여러 번 저장될 수 있었습니다.
- 애플리케이션 레벨 검증만으로는 동시 요청이나 예외 상황을 완전히 막기 어렵다고 판단했습니다.

### 해결방법과 그렇게 생각한 이유

- 복약 로그 한 건의 유일 기준을 `medication_id + taken_date + taken_index`로 정의했습니다.
- `taken_at`에서 날짜만 추출해 `taken_date`를 backfill하고, 이후 `NOT NULL`로 전환했습니다.
- DB에 복합 유니크 인덱스를 추가해 동일 복약 이벤트가 중복 저장되지 않도록 했습니다.
- 운영 중인 데이터를 고려해 `컬럼 추가 -> backfill -> NOT NULL 적용 -> 중복 그룹 점검 -> 유니크 인덱스 생성` 순서로 이행했습니다.
- 중복 그룹이 이미 있으면 인덱스 생성을 강행하지 않고 skip 하도록 설계했습니다.
- 이렇게 판단한 이유는 데이터 정합성은 서비스 코드의 의도만으로는 부족하고, DB 제약이 마지막 방어선이 되어야 하기 때문입니다.

### 성과

- 복약 로그 유일성 기준: 없음 -> `약 ID + 복용 날짜 + 복용 회차`
- 일 단위 날짜 컬럼: `0개 -> 1개`
- `taken_date NOT NULL` 제약: `0개 -> 1개`
- 복합 유니크 인덱스: `0개 -> 1개`
- 기존 중복 그룹 사전 점검 단계: `0개 -> 1개`
- 복약 통계와 PDF 리포트가 중복 로그로 왜곡될 가능성을 구조적으로 줄였습니다.

## 8. 회원 탈퇴 Cascade 리팩토링

### 상황

- 회원 탈퇴 시 서비스 레이어가 커뮤니티, 식단, 복약, 알림, 챌린지, 배지 등 관련 데이터를 순차적으로 삭제했습니다.
- 서비스 레이어 delete 호출 수가 `25회`였고, DB FK에 cascade가 있어도 애플리케이션이 같은 책임을 다시 구현하고 있었습니다.
- 관련 테이블이 늘어날수록 삭제 순서와 누락 위험이 커지는 구조였습니다.

### 해결방법과 그렇게 생각한 이유

- 연관 FK가 `ON DELETE CASCADE`로 연결된 상태를 기준으로, 서비스 레이어의 수동 delete 체인을 제거했습니다.
- 회원 탈퇴 시 사용자 row 삭제 1회만 수행하고, 참조 데이터 정리는 DB cascade에 맡겼습니다.
- 이렇게 판단한 이유는 참조 무결성과 연쇄 삭제는 DB가 더 일관되게 보장할 수 있는 책임이고, 애플리케이션은 "삭제 의도"만 명확히 표현하는 편이 유지보수에 유리하기 때문입니다.

### 성과

- 서비스 레이어 delete 호출 수: `25회 -> 1회`
- 회원 탈퇴 API 평균 응답시간: `51.14 ms -> 35.13 ms`
- 회원 탈퇴 API P95: `90.46 ms -> 69.66 ms`
- delete 호출 수 `96.00% 감소`, 평균 응답시간 `31.31% 감소`, P95 `22.99% 감소`
- 삭제 누락과 순서 의존성을 줄여 유지보수성을 개선했습니다.

## 9. 식단 수정 Diff Sync 전환

### 상황

- 식단 수정 시 기존 구조는 상위 식단 row를 수정한 뒤 기존 `diet_item`을 전부 삭제하고 요청 item을 전부 다시 insert했습니다.
- 실제로는 5개 중 1개만 바뀌어도 전체 삭제와 재삽입이 발생했습니다.
- 대표 5개 item 수정 기준 write 수는 `diet_log update 1 + diet_item delete all 1 + diet_item insert 5 = 총 7 writes`였습니다.

### 해결방법과 그렇게 생각한 이유

- 기존 item 목록과 요청 item 목록을 비교해 `유지 / 수정 / 삭제 / 추가`로 분기하는 diff sync 방식으로 바꿨습니다.
- 값이 바뀌지 않은 item은 write를 발생시키지 않고 유지했습니다.
- 변경된 item만 update하고, 새 item만 insert하며, 요청에서 빠진 기존 item만 delete했습니다.
- 이 방식을 선택한 이유는 수정 API는 "전체 교체"가 아니라 "변경분 반영"에 가깝게 동작해야 데이터가 많아질수록 효율적이라고 판단했기 때문입니다.

### 성과

- 대표 write 수: `7회 -> 4회`
- 식단 수정 API 평균 응답시간: `33.45 ms -> 16.93 ms`
- 식단 수정 API P95: `34.76 ms -> 21.41 ms`
- write 수 `42.86% 감소`, 평균 응답시간 `49.39% 감소`, P95 `38.41% 감소`
- unchanged item이 많을수록 효과가 커지는 구조로 개선했습니다.

## 10. 인증/세션 조회 공통화

### 상황

- 여러 컨트롤러에서 `session.getAttribute("loginUser")`를 직접 호출했습니다.

- baseline에서 로그인 사용자 직접 세션 조회 수는 `57회`였습니다.

### 해결방법과 그렇게 생각한 이유

- `SessionUserSupport` 같은 공통 컴포넌트로 로그인 사용자 조회를 모았습니다.

- 이렇게 판단한 이유는 세션 조회는 단순한 코드 중복이 아니라 인증 정책의 진입점이기 때문에, 흩어져 있으면 보안과 에러 처리 일관성이 깨질 수 있기 때문입니다.

### 성과

- 로그인 사용자 직접 세션 조회 수: `57회 -> 1회`
- 서비스 레이어 `HttpSession` 필드 주입 수: `1회 -> 0회`
- 직접 세션 조회 `98.25% 감소`, 서비스 레이어 세션 필드 주입 `100% 감소`
- 인증 실패 처리와 세션 사용자 갱신 위치를 명확히 할 수 있는 기반을 만들었습니다.

## 14. 챌린지 목록 N+1 집계 제거

- `GROUP BY` 집계를 통해 `successCount`, `failCount`, `successRate`를 한 번에 반환하도록 했습니다.
- 별도 통계 테이블도 고려할 수 있었지만, 현재 요구사항은 실시간성이 높고 집계 기준이 단순했기 때문에 조회 SQL 집계가 더 적합하다고 판단했습니다.

### 성과

- 진행 중 챌린지 `5개` 기준 DAO 호출 수: `11회 -> 1회`

## 15. 챌린지 하루 1회 로그 정책을 DB 제약으로 승격

### 상황

- 챌린지 로그는 서비스 레벨에서 같은 날짜 중복 여부를 먼저 조회했습니다.
- 하지만 DB에는 `user_challenge_id + log_date` 조합을 강제하는 유니크 제약이 없어, 동시 요청이나 우회 insert가 발생하면 중복 저장될 수 있었습니다.
- 운영 데이터에 이미 중복 그룹이 있으면 유니크 인덱스 생성 자체가 실패할 위험도 있었습니다.

### 해결방법과 그렇게 생각한 이유

- `user_challenge_id + log_date` 기준 복합 유니크 인덱스를 추가했습니다.
- 인덱스 생성 전에는 동일 조합의 중복 그룹 수를 먼저 조회하고, 중복 그룹이 없을 때만 인덱스를 생성하도록 했습니다.
- 서비스 검증은 사용자 경험을 위한 1차 방어선으로 유지하고, DB 유니크 인덱스를 동시성 상황의 최종 방어선으로 두었습니다.
- 이렇게 판단한 이유는 "하루 1회"는 명확한 비즈니스 규칙이므로 코드 규칙을 넘어 DB 제약으로 표현하는 것이 안전하기 때문입니다.

### 성과

- 챌린지 로그 일별 유니크 인덱스: `0개 -> 1개`
- 중복 방지 계층: `서비스 검증 1개 -> 서비스 검증 + DB 유니크 인덱스`
- 기존 중복 그룹 사전 점검 단계: `0개 -> 1개`

## 16. `user_challenge` 단일 라이프사이클 정책 명문화

### 상황

- 현재 도메인 정책은 한 사용자가 같은 챌린지에 대해 `PROGRESS -> GIVEUP -> REJOIN -> FINISH`를 같은 row에서 이어가는 방식이었습니다.
- 하지만 DB에 `user_id + challenge_id` 유니크 제약이 없으면, 동일 사용자/챌린지 조합이 여러 row로 쌓일 수 있습니다.
- 이 경우 최신 row만 찾기 위해 `ORDER BY DESC LIMIT 1` 같은 우회 로직에 의존하게 됩니다.

### 해결방법과 그렇게 생각한 이유

- `user_challenge(user_id, challenge_id)` 복합 유니크 인덱스를 추가했습니다.
- 인덱스 생성 전에는 동일 조합 중복 그룹을 점검하고, 중복이 없을 때만 생성하도록 했습니다.
- 동시 참여 요청으로 `DuplicateKeyException`이 발생할 수 있으므로, 서비스 레이어에서 비즈니스 예외로 전환했습니다.
- 이렇게 판단한 이유는 이미 서비스 정책이 "같은 row 재사용"이라면 DB 스키마도 같은 정책을 강제해야 코드와 데이터가 어긋나지 않기 때문입니다.

### 성과

- `user_challenge(user_id, challenge_id)` 유니크 인덱스: `0개 -> 1개`
- 중복 참여 요청에 대한 DB 안전장치: `0개 -> 1개`
- 기존 중복 그룹 사전 점검 단계: `0개 -> 1개`

- 상태 변경과 집계 값이 장기 운영 중 어긋나는 위험을 줄였습니다.

## 18. MediScan 임베딩 기반 알약 식별

### 상황

- 사용자는 약 이름을 모르는 상태에서 알약 이미지만으로 약을 찾고 싶어할 수 있습니다.
- 단순 이미지 유사도만으로는 색상, 각인, 앞/뒤면 차이 때문에 오탐이 생길 수 있습니다.
- 약품 식별은 정확도가 중요하므로 이미지 임베딩 결과를 그대로 반환하기보다 메타데이터 필터를 함께 적용해야 했습니다.

### 해결방법과 그렇게 생각한 이유

- 전면 이미지와 후면 이미지를 각각 임베딩 서버에 전송해 벡터를 생성했습니다.
- 두 임베딩을 평균해 query vector를 만들고, 로컬 `final_embedding.json`에서 cosine similarity 기준 Top 50 후보를 찾았습니다.
- 이후 각인(imprint)을 최우선 필터로 적용했습니다.
- 사용자가 앞면/뒷면을 바꿔 입력할 수 있으므로 정상 방향과 swapped 방향을 모두 허용했습니다.
- 그 다음 형태와 색상 필터를 적용하고, 각인이 일치하면 점수 보너스를 더해 최종 Top 5를 반환했습니다.
- 이렇게 판단한 이유는 이미지 임베딩은 후보 탐색에는 강하지만, 의약품 식별에서는 각인/색상/형태 같은 구조화 메타데이터가 정확도를 크게 보완할 수 있기 때문입니다.

### 성과

- 전면/후면 `2장`의 이미지를 사용해 평균 임베딩을 생성했습니다.
- 임베딩 차원은 `768`차원 기준으로 설계했습니다.
- 유사도 후보를 Top `50`까지 넓게 가져온 뒤, 각인/형태/색상 필터를 거쳐 최종 Top `5`로 줄였습니다.
- 각인 완전/부분 일치에 따라 `+0.1 ~ +0.2`, 단면 입력 일치에 `+0.15` 보너스를 적용해 메타데이터 기반 재랭킹을 구현했습니다.

## 19. 웹푸시 기반 복약 알림

### 상황

- 복약 서비스는 사용자가 정해진 시간에 약을 먹도록 도와야 합니다.
- 단순 화면 알림만으로는 사용자가 앱을 열지 않았을 때 알림을 받을 수 없습니다.
- 브라우저 push subscription, 사용자 push enabled 설정, 약별 알림 메시지를 연결하는 백엔드 파이프라인이 필요했습니다.

### 해결방법과 그렇게 생각한 이유

- `@Scheduled(cron = "0 * * * * *")`로 매 분 복약 알림 스케줄러를 실행했습니다.
- 현재 시간을 `HH:mm`으로 포맷하고, 알림 대상 복약 목록을 조회했습니다.
- 사용자 push 설정이 켜져 있는지 확인한 뒤, 해당 사용자의 push subscription 목록을 가져와 각 endpoint로 VAPID 웹푸시를 발송했습니다.
- payload에는 `title`, `body`, `medicationId`, `doseIndex`를 포함했습니다.
- 이렇게 판단한 이유는 프론트가 알림 클릭 후 어떤 약의 몇 번째 복용인지 바로 처리하려면 메시지 본문뿐 아니라 식별자도 payload에 포함되어야 하기 때문입니다.

### 성과

- 스케줄러 실행 주기: `1분마다 1회`, 하루 `1,440회`
- 사용자별 push enabled 설정을 확인해 불필요한 발송을 방지했습니다.
- 하나의 사용자에 여러 subscription이 있어도 목록을 순회하며 발송할 수 있게 했습니다.
- 알림 payload에 약 ID와 복용 회차를 포함해 프론트엔드 후속 처리와 연결했습니다.

## 20. 게이미피케이션 XP 정책과 중복 지급 방지

### 상황

- 식단 기록, 챌린지 성공, PDF 다운로드, 게시글/댓글 작성 등 여러 행동에 XP를 지급해야 했습니다.
- 클라이언트가 XP 값을 임의로 보내거나, 같은 행동을 여러 번 호출하면 포인트가 과다 지급될 수 있습니다.
- 일일 최대 XP, 댓글 횟수 제한, 스트릭 보너스, 레벨업 알림 등 정책이 복합적이었습니다.

### 해결방법과 그렇게 생각한 이유

- XP 값은 클라이언트 요청값을 신뢰하지 않고 서버의 `ActionType`별 정책으로 고정했습니다.
- 일일 XP cap을 `60`으로 두고, 남은 cap만큼만 지급했습니다.
- `xp_log`에 `(user_id, action_type, ref_id, earned_date)` 유니크 키를 두어 같은 행동의 중복 지급을 막았습니다.
- 하루 1회형 액션은 refId를 날짜로 강제했고, 끼니 기록이나 댓글처럼 개별 대상이 있는 액션은 대상 ID를 refId로 사용했습니다.
- 댓글 작성은 하루 `3회`까지만 XP를 지급하도록 별도 count를 두었습니다.
- 스트릭은 마지막 활동일 기준으로 연속성을 계산하고, 보너스도 일일 cap 안에서 지급했습니다.
- 이렇게 판단한 이유는 보상 시스템은 사용자 행동과 직접 연결되므로, 정책이 프론트나 호출 순서에 의존하면 쉽게 악용되거나 데이터가 왜곡될 수 있기 때문입니다.

### 성과

- 일일 XP cap: `60`
- 마스터 XP cycle: `500`
- 댓글 XP 지급 제한: 하루 `3회`
- 중복 지급 방지 유니크 키: `1개`
- 레벨업 시 notification feed와 연동해 사용자에게 성장 이벤트를 전달했습니다.
- `DuplicateKeyException`을 중복 지급 결과로 변환해 재시도/중복 클릭 상황에서도 안정적으로 응답할 수 있게 했습니다.

- 컨트롤러나 PDF 서비스에서 직접 계산을 모두 처리하면 템플릿 렌더링과 도메인 계산이 섞일 위험이 있었습니다.

## 22. 파일 업로드 저장 안정성 개선

### 상황

- 식단 사진, 커뮤니티 이미지 등 사용자 업로드 파일을 서버에 저장해야 했습니다.
- 파일명에 경로 문자가 포함되거나, 저장 디렉터리가 존재하지 않거나, 운영 환경별 업로드 위치가 달라질 수 있었습니다.

### 해결방법과 그렇게 생각한 이유

- 업로드 디렉터리를 설정값으로 받고, 저장 전에 `Files.createDirectories()`로 대상 디렉터리를 생성했습니다.
- 원본 파일명은 `StringUtils.cleanPath()`로 정리하고, `System.currentTimeMillis()` prefix를 붙여 파일명 충돌 가능성을 줄였습니다.
- 저장 경로를 normalize한 뒤, 최종 파일 경로가 target directory 안에 있는지 `startsWith`로 검증했습니다.
- 이렇게 판단한 이유는 업로드 기능은 사용자 입력이 파일 시스템 경로로 이어지는 민감한 지점이라, 편의성보다 경로 조작 방지가 우선이라고 봤기 때문입니다.

### 성과

- 업로드 경로를 코드 literal이 아니라 설정값으로 관리했습니다.
- 저장 전 디렉터리 자동 생성으로 환경 초기화 부담을 줄였습니다.
- 경로 이탈 검증을 통해 `../` 형태의 path traversal 위험을 차단했습니다.

## 23. 챌린지 채팅 참여 권한 검증

### 상황

- 챌린지별 채팅은 해당 챌린지에 참여 중인 사용자만 메시지를 보낼 수 있어야 했습니다.
- 단순히 userId와 challengeId만 받으면, 사용자가 참여하지 않은 챌린지에 메시지를 쓰는 문제가 생길 수 있습니다.

### 해결방법과 그렇게 생각한 이유

- 메시지 저장 전 `userChallengeDao.selectByUserAndChallenge(userId, challengeId)`로 참여 정보를 조회했습니다.
- 참여 row가 없거나 상태가 `PROGRESS`가 아니면 예외를 발생시켜 저장하지 않았습니다.
- 메시지에는 userId만 저장하지 않고, userDao에서 nickname을 조회해 함께 저장했습니다.
- 이렇게 판단한 이유는 실시간/커뮤니티 기능에서는 쓰기 권한 검증이 누락되면 데이터 오염과 사용자 신뢰 문제가 바로 발생하기 때문입니다.

### 성과

- 채팅 메시지 저장 전 참여 상태 검증 단계를 `1회` 추가했습니다.
- 허용 상태를 `PROGRESS`로 제한해 포기/종료된 챌린지의 메시지 작성을 차단했습니다.
- 메시지 저장 시 nickname을 함께 기록해 조회 화면에서 추가 사용자 조회 부담을 줄일 수 있게 했습니다.

## 24. Flyway 기반 스키마 이력 관리

### 상황

- 프로젝트에는 사용자, 의료, 식단, 커뮤니티, 챌린지, 알림, 게이미피케이션 등 여러 도메인 테이블이 존재합니다.
- 기능이 늘어날수록 로컬 DB와 운영 DB의 스키마 차이가 생기기 쉽습니다.
- 특히 유니크 인덱스, cascade, 신규 컬럼 같은 변경은 적용 순서가 중요합니다.

### 해결방법과 그렇게 생각한 이유

- `src/main/resources/db/migration` 아래에 Flyway migration 파일을 버전별로 관리했습니다.
- `V1` 사용자/푸시 구독, `V2` 의료, `V3` 식단, `V4` 커뮤니티, `V5` 챌린지, `V6` 알림/게이미피케이션, `V7` 복약 로그 유니크 키 정비처럼 도메인별 이력을 분리했습니다.
- 운영 데이터가 있는 변경은 컬럼 추가, backfill, NOT NULL, 중복 점검, 인덱스 생성 순서로 쪼갰습니다.
- 이렇게 판단한 이유는 DB 변경은 코드처럼 한 번에 되돌리기 어렵고, 이행 순서 자체가 안정성의 핵심이기 때문입니다.

### 성과

- migration 파일 수: `7개`
- 알림/게이미피케이션 migration에서 `notification`, `user_progress`, `daily_xp`, `xp_log`, `user_streak`, `user_badge` 등 `6개` 테이블을 추가했습니다.
- 복약 로그 migration은 기존 데이터 backfill과 중복 그룹 점검까지 포함해 운영 이행 안정성을 고려했습니다.

## 25. 알림 피드와 도메인 이벤트 연결

### 상황

- 복약 알림, 레벨업, 챌린지, 커뮤니티 등 사용자에게 알려야 할 이벤트가 여러 도메인에 흩어져 있었습니다.
- 단순 push만 보내면 사용자가 앱 안에서 지난 알림을 확인하기 어렵고, push 실패 시 이벤트 이력이 남지 않을 수 있습니다.

### 해결방법과 그렇게 생각한 이유

- notification feed 테이블을 두고, `type`, `target_type`, `target_id`, `is_read`, `created_at`을 저장하도록 설계했습니다.
- 게이미피케이션 레벨업 시 `NotificationFeedService.notify()`를 호출해 알림 피드와 도메인 이벤트를 연결했습니다.
- 최근 알림, 전체 알림, 미읽음 개수, 개별 읽음, 최근 읽음, 전체 읽음, batch 읽음 API를 제공했습니다.
- 이렇게 판단한 이유는 알림은 단순 메시지 발송이 아니라 사용자 행동을 다시 도메인 객체로 연결하는 내비게이션 역할도 하기 때문입니다.

### 성과

- 알림 피드 테이블: `1개`
- 읽음 상태 컬럼: `is_read`
- 알림 조회/읽음 처리 API: 최근, 전체, 미읽음 수, 개별 읽음, 최근 읽음, 전체 읽음, batch 읽음 등 `7개` 흐름
- push와 별개로 앱 내부 알림 이력을 남길 수 있는 기반을 만들었습니다.

## 26. 백엔드 규모와 리팩토링 안전망 확장

### 성과

- main Java 파일 수: `194개`
- test Java 파일 수: baseline `1개`, 현재 `4개`
- 리팩토링 기록상 주요 개선 항목별 검증 테스트 통과 내역을 남겼습니다.
- 성능 개선뿐 아니라 "어떤 조건에서 검증했는지"를 기록해 포트폴리오 신뢰도를 높였습니다.

## 27. Spring Batch 기반 복약 알림 Outbox 파이프라인 고도화

### 상황

- 기존 복약 알림은 `@Scheduled`가 정해진 시각마다 직접 복약 대상을 조회하고 WebPush 발송까지 수행하는 구조였습니다.
- 이 구조에서는 대량 대상 조회, 중복 발송 방지, 개별 실패 기록, 재시도, 장애 후 재실행 기준이 명확히 분리되어 있지 않았습니다.
- 특히 DB 저장과 외부 WebPush 발송이 같은 흐름에 섞이면, WebPush는 성공했지만 DB 저장이 실패하거나 반대로 DB에는 성공으로 남았지만 실제 발송은 실패하는 불일치가 생길 수 있다고 판단했습니다.
- 또한 스케줄러가 정각에 항상 실행된다는 보장이 없기 때문에, 단일 `notificationTime` 기준보다 업무 시간 슬롯 기준의 배치 처리가 필요했습니다.

### 해결방법과 그렇게 생각한 이유

- `@Scheduled`는 실행 시점만 결정하고, 실제 대량 처리와 상태 관리는 Spring Batch Job이 담당하도록 역할을 분리했습니다.
- `MedicationNotificationJob`을 `prepareNotificationStep -> sendNotificationStep -> summarizeNotificationStep` 흐름으로 설계했습니다.
- `prepareNotificationStep`에서는 `slotStart <= scheduledAt < slotEnd` 반열린 시간 구간 기준으로 복약 회차를 계산하고, 발송 대상 알림을 `PENDING` Outbox로 먼저 영속화했습니다.
- 동일 복약 회차의 중복 생성을 막기 위해 `user_id + medication_id + scheduled_at + dose_sequence` 유니크 키를 두고, `ON DUPLICATE KEY UPDATE` 기반 멱등 저장을 적용했습니다.
- `sendNotificationStep`에서는 `PENDING/RETRY` 대상만 조회한 뒤 조건부 UPDATE로 `PROCESSING` 상태를 선점하고, Claim Token과 Lease를 함께 저장했습니다.
- WebPush 발송은 DB 트랜잭션 밖에서 수행하고, 발송 결과 저장은 별도 짧은 트랜잭션으로 처리하도록 분리했습니다. 이렇게 판단한 이유는 외부 발송은 DB 트랜잭션으로 롤백할 수 없기 때문에, Chunk Writer의 일반적인 retry에 섞으면 이미 발송된 알림이 재실행될 위험이 있기 때문입니다.
- 재시도 정책은 `attempt_count`, `next_retry_at`, `maxAttempts=3` 기준으로 정의했습니다. 선점 성공 시점에 `attempt_count`를 증가시켜, 서버가 발송 중 종료되더라도 실제 처리 시도 사실이 남도록 했습니다.
- 장시간 `PROCESSING`에 머문 데이터는 `MedicationNotificationRetryJob`에서 Lease 만료 기준으로 `RETRY` 또는 `FAILED`로 복구하고, 이전 Claim 정보를 초기화하도록 설계했습니다.
- 알림 메시지는 prepare 시점에 `notification_title`, `notification_body`, `payload_json` 스냅샷으로 고정하고, 실제 Subscription 목록은 send 시점에 조회하도록 나눴습니다.
- Spring Batch 메타 테이블과 Outbox 테이블은 Flyway migration으로 관리해, 스키마 자동 생성과 마이그레이션 관리가 섞이지 않도록 했습니다.

### 성과

- 기존 `@Scheduled` 직접 발송 구조를 Spring Batch + Outbox + Claim Token/Lease 기반의 운영형 알림 파이프라인으로 확장했습니다.
- Outbox 상태를 `PENDING`, `PROCESSING`, `SENT`, `RETRY`, `FAILED`, `SKIPPED`로 명확히 정의해, 장애 이후에도 미처리/재처리 대상을 상태 기준으로 식별할 수 있게 했습니다.
- 동일 업무 슬롯의 중복 실행에서도 Outbox 중복 생성이 발생하지 않도록 DB 유니크 제약과 멱등 저장을 적용했습니다.
- 두 Worker가 같은 Outbox를 동시에 선점하는 상황에서도 조건부 UPDATE로 하나의 실행만 `PROCESSING` 전환에 성공하도록 검증했습니다.
- Testcontainers MySQL 통합 테스트를 추가해 실제 MySQL 유니크 제약, 동시 claim, stale claim token, Lease 만료 복구, EXPLAIN 기반 인덱스 선택을 검증했습니다.
- 실제 테스트 결과는 `Tests run: 20, Failures: 0, Errors: 0, Skipped: 0`, `BUILD SUCCESS`로 기록했습니다.
- 통합 테스트 과정에서 MySQL의 `ON DUPLICATE KEY UPDATE` no-op도 affected rows가 `1`로 반환될 수 있음을 확인했고, JDBC 반환값이 아니라 `origin_job_execution_id` 기준 실제 생성 행 수로 `createdCount`를 집계하도록 수정했습니다.
- 이 경험을 통해 단순 기능 구현보다 운영 중 장애, 재시도, 재실행, 중복 방지, 실제 DB 동작 차이까지 고려해 배치 파이프라인을 설계한 사례로 설명할 수 있습니다.

## 28. 공공 의약품 데이터 기반 챗봇 RAG 구조 고도화

### 상황

- 기존 챗봇은 GPT API 호출을 중심으로 답변을 생성하는 구조였고, 사용자 복약 데이터와 식약처 의약품 데이터를 질문 의도에 맞게 선별해 전달하는 책임이 명확히 분리되어 있지 않았습니다.
- 사용자가 "오늘 저녁에 먹을 약이 뭐야?", "타이레놀 부작용 알려줘", "내가 먹는 약 중 술 조심해야 하는 약이 있어?"처럼 질문했을 때, 개인 복약 상태와 일반 의약품 정보를 같은 방식으로 처리하면 정확성과 개인정보 최소 전달 측면에서 문제가 생길 수 있다고 판단했습니다.
- 또한 식약처 원문에는 효능, 복용법, 주의사항, 부작용, 상호작용처럼 긴 문단형 데이터가 포함되어 있어, 단순 키워드 검색만으로는 자연어 질문과 의미적으로 가까운 근거 문단을 찾기 어렵다고 보았습니다.
- 따라서 단순 GPT 챗봇이 아니라, 개인 복약 데이터와 공공 의약품 데이터를 분리 조회하고, 검색된 근거만 LLM에 전달하는 근거 기반 응답 구조로 고도화할 필요가 있었습니다.

### 해결방법과 그렇게 생각한 이유

- 정확한 상태 조회가 필요한 사용자 등록 약, 복용 시간, 오늘 복용 여부는 MySQL에서 조회하고, 긴 부작용·주의사항·상호작용 문서는 Vector DB에서 의미 기반으로 검색하도록 역할을 분리했습니다.
- 질문을 `PERSONAL_MEDICATION`과 `GENERAL_DRUG_INFO` 범위로 나누고, 다시 일정, 복용 여부, 효능, 복용법, 부작용, 주의사항, 상호작용 의도로 분류해 필요한 데이터만 Context로 구성하도록 설계했습니다.
- 일반 의약품 질문은 질문에 언급된 약품명을 기준으로 식약처 DB 데이터를 우선 조회하고, DB에 없거나 오래된 항목은 공공 API를 통해 보완하는 cache-first + fallback 구조로 정리했습니다.
- LLM에는 전체 약품 원문을 그대로 넘기지 않고, 질문 의도에 맞는 Section만 전달하도록 제한했습니다. 이렇게 판단한 이유는 토큰 비용을 줄이고, 관련 없는 정보가 섞여 답변 근거가 흐려지는 문제를 줄이기 위해서입니다.
- 응답에는 약품명, 품목기준코드, 근거 출처, 조회 시점을 포함하고, 제공된 근거에 없는 내용은 추측하지 않도록 시스템 지시와 응답 생성 책임을 서비스 계층에 분리했습니다.
- Vector Retrieval 확장을 위해 `rag_document`, `rag_chunk`, `rag_index_job` 모델을 추가하고, 문서의 유효 상태와 인덱싱 작업 상태를 분리했습니다.
- 문서 상태는 `INDEXING`, `ACTIVE`, `OBSOLETE`, `DELETED`로 관리하고, 인덱싱 작업 상태는 `PENDING`, `PROCESSING`, `RETRY`, `COMPLETED`, `FAILED`로 관리하도록 나눴습니다. 이렇게 판단한 이유는 문서가 검색 가능한 상태인지와 임베딩 작업이 성공했는지는 서로 다른 생명주기를 갖기 때문입니다.
- 식약처 데이터는 약 전체가 아니라 `itemSeq + sectionType` 기준 Section 단위로 `contentHash`를 계산해, 변경되지 않은 Section은 재인덱싱하지 않고 변경된 Section만 새 `documentVersion`으로 Chunk를 생성하도록 설계했습니다.
- Spring AI `VectorStore`와 Qdrant를 연결해 `rag_chunk`를 `Document`로 변환하고, `itemSeq`, `sectionType`, `documentVersion`, `ragDocumentId`, `ragChunkId`를 metadata로 저장하는 기본 Vector Retrieval 경로를 구현했습니다.
- Qdrant 직접 저장 경로와 Spring AI 저장 경로가 섞이면 중복 저장이나 Point ID 불일치가 생길 수 있다고 판단해, 초기 저장·검색 책임은 Spring AI `VectorStore` 하나로 두고 Qdrant Native Client는 추후 Collection 관리나 Payload Index 생성처럼 전용 관리 기능에만 사용하는 방향으로 정리했습니다.

### 성과

- 기존 GPT 호출 중심 챗봇을 RDB/API 기반 Grounded Chatbot 구조로 정리하고, 개인 복약 질문과 일반 의약품 질문을 분리할 수 있는 기반을 만들었습니다.
- 사용자 복약 데이터는 MySQL에서 정확히 조회하고, 의약품 원문 데이터는 식약처 DB/API 근거를 통해 구성하도록 분리해 답변의 근거성과 개인정보 최소 전달 원칙을 강화했습니다.
- 식약처 의약품 정보 조회는 DB 우선 조회 후 필요한 경우 공공 API로 보완하는 구조로 정리해, 외부 API 의존도를 줄이고 응답 안정성을 높였습니다.
- RAG 확장을 위해 `rag_document`, `rag_chunk`, `rag_index_job` 테이블을 설계하고, Section 단위 `contentHash`, `documentVersion`, `lifecycleStatus`, `jobStatus`를 통해 변경 감지와 인덱싱 상태 추적 기반을 마련했습니다.
- Spring AI VectorStore + Qdrant 기본 연결을 추가해 Chunk 저장, metadata filter 기반 유사도 검색, documentVersion 기준 삭제 경로를 구현했습니다.
- 관련 단위 테스트를 추가해 질문 분류, Context 구성, DrugInfo cache fallback, RAG 문서 생성, VectorStore 저장·검색·삭제 흐름을 검증했습니다.
- 현재까지 주요 챗봇/RAG 관련 검증은 `Tests run: 19, Failures: 0, Errors: 0`, `BUILD SUCCESS`로 통과했습니다.
- 이 경험은 단순히 "챗봇을 만들었다"가 아니라, 공공 데이터 수집·저장·변경 감지·문서 분할·Vector 검색·근거 기반 응답까지 이어지는 백엔드 데이터 처리 시스템으로 설명할 수 있습니다.

## 29. 전역 예외 처리와 API 에러 응답 표준화

### 상황

- 여러 REST API가 `ResponseEntity`를 직접 반환하면서, 컨트롤러별로 에러 응답 형식이 달라질 수 있는 구조였습니다.
- 인증 실패, 잘못된 요청, 서버 내부 오류가 각기 다른 형태로 내려가면 프런트엔드에서는 API마다 별도 분기 처리를 해야 합니다.
- 또한 예상하지 못한 예외가 그대로 노출되면 내부 구현 정보가 사용자에게 전달될 위험이 있고, 반대로 로그가 남지 않으면 원인 추적이 어려워집니다.

### 해결방법과 그렇게 생각한 이유

- `@RestControllerAdvice` 기반 `GlobalExceptionHandler`를 두어 REST API 예외 응답의 공통 진입점을 만들었습니다.
- `ResponseStatusException`은 예외에 담긴 HTTP status와 reason을 유지해, 서비스 계층에서 의도한 비즈니스 실패를 그대로 표현하도록 했습니다.
- `IllegalArgumentException`은 `400 Bad Request`로 변환해 잘못된 입력에 대한 응답을 통일했습니다.
- 예상하지 못한 `Exception`은 서버 로그에 stack trace를 남기되, 클라이언트에는 `"서버 처리 중 오류가 발생했습니다."`라는 일반화된 메시지만 반환하도록 했습니다.
- 이렇게 판단한 이유는 예외 처리를 컨트롤러마다 흩어두면 API가 늘어날수록 응답 형식과 보안 수준이 달라지고, Spring MVC가 제공하는 전역 처리 지점을 활용하는 편이 유지보수에 유리하기 때문입니다.

### 성과

- 전역 예외 처리 컴포넌트: `GlobalExceptionHandler` `1개`
- 공통 처리 예외 유형: `ResponseStatusException`, `IllegalArgumentException`, `Exception` 총 `3개`
- API 에러 응답 형식을 `{ "message": "..." }` 구조로 맞출 수 있는 기반을 만들었습니다.
- 서버 내부 오류는 로그로 남기고, 클라이언트에는 내부 stack trace나 구현 정보를 노출하지 않도록 분리했습니다.
- 이 사례는 단순 CRUD 구현이 아니라 Spring MVC의 전역 예외 처리 흐름을 활용해 API 품질과 운영 디버깅 가능성을 함께 개선한 경험으로 설명할 수 있습니다.

## 30. WebClient 기반 외부 LLM/GMS 연동 분리

### 상황

- 챗봇 기능은 내부 복약/의약품 근거 데이터를 조립한 뒤 외부 LLM/GMS API에 요청을 보내야 했습니다.
- 외부 API base URL, 인증 헤더, 모델명, 요청 body 조립, 응답 파싱이 한 곳에 뒤섞이면 테스트와 설정 변경이 어려워지고, 민감한 API 키가 코드에 남을 위험도 있습니다.
- 사용자 질문 입력은 빈 문자열이나 과도하게 긴 문자열을 사전에 걸러야 했고, LLM 응답이 비어 있거나 형식이 달라도 서비스가 안전하게 fallback 해야 했습니다.

### 해결방법과 그렇게 생각한 이유

- `GmsClientConfig`에서 `WebClient` Bean을 생성하고, `gms.base-url`, `gms.api-key` 설정값으로 base URL과 Authorization header를 주입하도록 분리했습니다.
- 챗봇 컨트롤러는 `@Valid @RequestBody`로 요청 DTO를 검증하고, `ChatRequest`에는 `@NotBlank`, `@Size(max = 1000)` 제약을 두었습니다.
- `ChatbotServiceImpl`에서는 먼저 `ChatbotContextService`가 만든 근거 컨텍스트를 받고, 그 컨텍스트와 사용자 질문을 외부 API 요청 body로 조립했습니다.
- 모델명은 `${gms.model:gpt-4.1}` 프로퍼티로 외부화해, 코드 변경 없이 환경별 모델 교체가 가능하도록 했습니다.
- 외부 응답은 `GmsResponse` DTO로 역직렬화한 뒤, output/content/text 구조를 순회해 답변 텍스트만 추출했습니다.
- 응답이 비어 있거나 예상 구조와 다르면 `"AI 답변을 가져오지 못했습니다."`로 fallback 하도록 했습니다.
- 이렇게 판단한 이유는 외부 AI 연동은 비즈니스 로직보다 장애와 설정 변경 가능성이 크기 때문에, HTTP client 설정, 요청 검증, 근거 컨텍스트 조립, 응답 파싱 책임을 분리해야 안전하게 확장할 수 있다고 봤기 때문입니다.

### 성과

- 외부 LLM/GMS 호출 경로를 `WebClient Bean 설정 -> 요청 검증 -> 근거 Context 조립 -> 외부 API 호출 -> 응답 텍스트 추출` 흐름으로 분리했습니다.
- 챗봇 요청 검증 제약: `@NotBlank` `1개`, `@Size(max = 1000)` `1개`
- 설정 외부화 항목: `gms.base-url`, `gms.api-key`, `gms.model`
- 외부 API 응답이 비어 있는 경우에도 사용자에게 안전한 fallback 메시지를 반환하도록 했습니다.
- 이 사례는 Spring Boot에서 외부 HTTP client를 설정 주입 기반으로 구성하고, validation과 DTO 파싱을 포함해 API 연동 경계를 설계한 개발 역량으로 어필할 수 있습니다.

## 31. STOMP WebSocket 기반 실시간 챌린지 채팅 구현

### 상황

- 챌린지 기능은 사용자가 같은 챌린지 안에서 실시간으로 메시지를 주고받고, 과거 채팅 이력도 다시 조회할 수 있어야 했습니다.
- 단순 REST polling으로 구현하면 메시지 도착 지연과 불필요한 반복 요청이 늘어날 수 있습니다.
- 반대로 WebSocket만 사용하면 최초 입장 시 과거 메시지 조회와 실시간 메시지 발행 책임이 섞일 수 있어, REST 조회 경로와 실시간 발행 경로를 분리할 필요가 있었습니다.

### 해결방법과 그렇게 생각한 이유

- `@EnableWebSocketMessageBroker` 기반 STOMP 메시지 브로커를 설정했습니다.
- WebSocket endpoint는 `/ws-chat`, 애플리케이션 publish prefix는 `/pub`, subscribe prefix는 `/sub`로 나누었습니다.
- 클라이언트가 `CONNECT`할 때 전달한 `userId`를 STOMP session attribute에 저장하고, 메시지 처리 시 이 값을 꺼내 `ChatMessageDto.userId`에 주입하도록 했습니다.
- 메시지 전송은 `@MessageMapping("/chat/send")`에서 받고, 저장은 `chatService.sendMessage(dto)`에 맡긴 뒤 `SimpMessagingTemplate`으로 `/sub/chat/room/{challengeId}`에 broadcast했습니다.
- 과거 메시지 조회는 `GET /api/challenge/{challengeId}/chat` REST API로 분리해, 초기 로딩과 실시간 수신의 책임을 나눴습니다.
- 이렇게 판단한 이유는 실시간 기능에서도 "이력 조회는 REST, 신규 이벤트 전파는 WebSocket"으로 경계를 나누면 프런트엔드 흐름이 단순해지고, 서버에서도 저장 책임과 전파 책임을 명확히 유지할 수 있기 때문입니다.

### 성과

- WebSocket endpoint: `/ws-chat`
- STOMP publish/subscribe prefix: `/pub`, `/sub`
- 실시간 메시지 처리 mapping: `/chat/send`
- 챌린지별 subscribe destination: `/sub/chat/room/{challengeId}`
- 과거 채팅 조회 REST API: `GET /api/challenge/{challengeId}/chat`
- 메시지 저장과 실시간 broadcast를 한 흐름으로 연결하면서도, 조회와 발행 경로를 분리했습니다.
- 이 사례는 Spring WebSocket/STOMP, session attribute, `SimpMessagingTemplate`을 활용해 실시간 기능을 구현한 Java/Spring Boot 개발 경험으로 설명할 수 있습니다.

## 32. JPA/Querydsl/MyBatis/JDBC 혼합 영속성 전략 정리

### 상황

- 프로젝트는 사용자, 복약, 식단, 챌린지, 알림, RAG 등 도메인이 많고, 조회 패턴도 단순 CRUD부터 집계 SQL, 동시성 제어용 조건부 UPDATE까지 다양했습니다.
- 모든 데이터 접근을 하나의 기술로 통일하면 단순 CRUD에는 편하지만, 복잡한 SQL이나 배치성 갱신에서는 표현력과 성능 제어가 떨어질 수 있습니다.
- 반대로 SQL 중심으로만 작성하면 도메인 관계가 명확한 영역에서 객체 모델과 트랜잭션 경계를 표현하기 어렵습니다.

### 해결방법과 그렇게 생각한 이유

- 메인 애플리케이션에는 `@MapperScan("com.medeat.**.dao")`를 적용해 기존 MyBatis DAO와 XML mapper 기반 SQL을 유지했습니다.
- 사용자, 복약, 복약 로그, 복약 스케줄, 의료 정보처럼 관계와 생명주기가 중요한 영역은 JPA Entity와 `JpaRepository`로 모델링했습니다.
- 복약 조회처럼 타입 안정성과 동적 조건 조합이 필요한 경로는 `JPAQueryFactory` Bean을 두고 Querydsl Repository로 분리했습니다.
- `MedicationQueryRepository`에서는 `QMedication`, `QMedicationLog`, `QMedicationSchedule`을 사용해 DTO projection을 직접 구성하고, 알림 대상 조회는 `medication_schedule.intake_time` 동등 비교 조건으로 표현했습니다.
- Batch Outbox나 RAG 문서 DAO처럼 조건부 UPDATE, upsert, named parameter가 중요한 영역은 `NamedParameterJdbcTemplate` 기반 Repository로 분리했습니다.
- 이렇게 판단한 이유는 백엔드 개발에서 중요한 것은 특정 기술 하나를 고집하는 것이 아니라, 도메인 관계·쿼리 복잡도·동시성 제어 요구에 맞춰 영속성 도구를 선택하는 것이라고 봤기 때문입니다.

### 성과

- MyBatis scan 범위: `com.medeat.**.dao`
- JPA 기반 Repository: 사용자, 복약, 복약 로그, 복약 스케줄, 의료 정보 등 핵심 도메인에 적용
- Querydsl 설정: `JPAQueryFactory` Bean `1개`
- Querydsl 조회 Repository: `MedicationQueryRepository`
- JDBC 기반 특수 Repository: 복약 알림 Outbox, RAG 문서 DAO 등 상태 전이와 대량 SQL이 필요한 영역에 적용
- 단순 CRUD, 타입 안정적인 조건 조회, 복잡 SQL/상태 전이를 각각 다른 도구로 분리해 개발 생산성과 쿼리 제어력을 함께 확보했습니다.
- 이 사례는 Java/Spring Boot 백엔드에서 JPA, Querydsl, MyBatis, JDBC를 무작정 섞은 것이 아니라 각 기술의 강점에 맞게 경계를 설계한 경험으로 어필할 수 있습니다.
